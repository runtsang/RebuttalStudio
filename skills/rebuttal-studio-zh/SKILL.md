# Rebuttal Studio（中文版）

## 概述

把 Rebuttal Studio 编辑器的五阶段流程搬到对话里来做。**说什么**由作者决定；这个 skill 负责**怎么**组织、排版和润色。

核心原则：回复里的每一句话都能追溯到作者。只有作者才知道的内容放进占位，不靠猜。

## 约定

以下约定在每个阶段都成立。

1. **句子的来源。** 回复正文里的每一句话，只能是下面四种之一：(a) 作者要点的转述；(b) 从作者提供的文件（论文、实验结果、日志）里读到的事实，并注明出处；(c) 礼貌开场句或过渡句；(d) 占位：`[AUTHOR INPUT NEEDED: 缺什么]`。审稿意见只能说明 reviewer 说了什么（引文、认可的优点），不能当作关于论文的事实来源。本 skill 文件里的示例只用来展示格式，不能当作事实来源。
2. **占位。** 缺一项信息就留一个占位。作者完全没有提到的问题，正文只留一个占位，写明回答这个问题需要什么。
3. **引用。** reviewer 的话原样照抄，必须是审稿意见原文中的连续片段。一条意见被拆成几个问题时，每一段仍然是原文的连续片段：连接词（"and"、"Also,"）和紧挨着它的标点不带，片段可以以小写字母开头。
4. **格式。** `references/templates.md` 里的模板逐字符照抄，只改方括号部分和 `{{placeholders}}`。
5. **状态。** 还有占位没填的文档是草稿，交付时附上带编号的占位清单。一个占位都没有的文档才能说“可以提交”。
6. **语言。** 用作者使用的语言和作者交流。Rebuttal 正文用英文写，除非作者另有要求。
7. **确认点。** 每个阶段的结果先给作者看，得到确认后再进入下一阶段。作者要求一次跑完时，把现有输入能支持的阶段全部做完（首轮回复做到 Stage 3 为止），并按约定 5 交付。

## 准备

缺什么就问什么，在一条消息里一次问完：

- 会议、submission 编号、每位 reviewer 的 ID 和完整审稿意见。
- 每条评论的长度上限，以及按字符还是按单词计算。
- 主题色，用 6 位十六进制表示（默认 `#f26921`，橙色）。作者用文字说颜色时，按模板 1 的对应关系取值，并告诉作者用的是哪个色值。
- 论文源文件和实验结果文件（如果有）。

把工作内容保存成文件，后面几轮可以接着做：

```
rebuttal/
├── paper-memory.md            # 可选：论文的背景摘要
├── <reviewerId>/
│   ├── breakdown.md           # Stage 1
│   ├── replies.md             # Stage 2：每个问题的要点和润色后的回复
│   ├── first-round.md         # Stage 3：状态和占位清单，然后是可直接粘贴的各部分
│   └── followups.md           # Stage 4：压缩上下文和每一轮追问
├── final-remarks.md           # Stage 5
└── messages.md                # 可选：催促 reviewer 的消息和给 AC 的说明
```

有论文时，按模板 11 的标题写 `paper-memory.md`。它只是背景资料，不能凌驾于审稿意见和作者的要点之上。

## Stage 1 - Breakdown

每位 reviewer 按模板 6 写一份 `breakdown.md`：

1. 提取该会议的各项评分，只保留数字。字段映射见 `references/venues.md`。
2. 原样抄录 summary 和 strengths。
3. 把所有需要回应的部分拆成原子问题，每个问题只包含一个独立的关注点或请求。以下情况要拆：用 "and"、"also"、"in addition"、"furthermore" 连起来的多个请求；同一条里话题发生了转换；多个不同的可操作请求；一条里混有不同类型的问题。围绕同一个关注点展开的几句话不拆。
4. `weaknessN` 和 `questionN` 分别编号，按出现的先后顺序排。编号跟着原子问题走，不跟 reviewer 自己的条目编号走。
5. 每个问题对应一条 response 记录：简短标题（"Regarding ..."）、`source`、`source_id`、`quoted_issue`。
6. 检查：每个问题只出现一次，只对应一条 response，并且一字不差。

把问题列表给作者看。作者可以合并、拆分、改标题或调整顺序。

## Stage 2 - Reply

在 `replies.md` 里逐个问题处理（每条记录的格式见模板 7）：

1. **先有要点。** 收集作者的要点：直接的结论、证据、论文里改了什么。为了帮作者理清思路，可以建议评论类型和回复策略（`references/quality.md` 第 1 节）。作者提供了论文或实验结果文件时，可以根据文件起草一份要点，标注为 “Proposed outline (unconfirmed)”，并注明每条事实的出处。没有要点的问题不做润色：它的记录里写 `Outline: (none yet)`，润色稿就是一个占位（约定 2）。
2. **润色。** 把要点写成模板 7 的工作格式：
   - 开场句可以不用：要用的话最多一句，从开场句库里按 reviewer 的意图选；没有合适的就不用（单纯的事实性问题直接回答）。
   - 前两句之内就要回到被引用的问题上。
   - 面对新颖性质疑，说清楚新在哪里、为什么重要、和已有工作有什么不同。
   - 每个要点一个短段落，不同的要点不要合并。
   - 表格写成 Markdown 表格，代码放进代码块，公式用 `$...$` 或 `$$...$$`。
   - 每个技术论断的意思保持不变。承诺不超出要点里答应的范围。
   - 新引用必须先核实才能加入（`references/quality.md` 第 5 节）。
3. 作者对润色稿的修改就是最终版本。

## Stage 3 - First Round

为每位 reviewer 组装 `first-round.md`：

1. 开头段（模板 3），把 `A`、`B`、`C` 换成这位 reviewer 认可的优点。
2. 按 breakdown 的顺序，每个问题一个 point-to-point 回复块（模板 2）：带颜色的标题 `R<n>: Regarding ...`、引用标签和原文引用、带颜色的 Response 标签、正文。
3. 结尾段（模板 3）。
4. 用工具（`wc -m` 或一小段脚本）统计 Markdown 源码的字符数，不要估算。超过上限时，在回复块之间拆分，并给每一部分加上标题行（模板 5）。带占位的草稿按现状统计，并说明占位填完之后需要重新统计、重新拆分。
5. 过一遍自查清单（`references/quality.md` 第 4 节）。只向作者报告没通过或无法核实的条目；清单本身不要放进可粘贴的部分里。

每一部分放在一个代码块里交付，前面写上它的标题行和字符数。

## Stage 4 - Multi Rounds

在 `followups.md` 里逐条处理追问（每条记录的格式见模板 8）：

1. 把这位 reviewer 的首轮文档压缩成 `Key Question(s)` / `Main Answer(s)`（模板 8）。`first-round.md` 有改动时重新压缩。
2. 原样记录追问，并收集作者的回复要点。
3. 写回复：开头几句直接回答；内容以压缩上下文和作者的要点为依据；和首轮保持一致；需要时指回之前的回复（"As noted in our Response W2, ..."）。一到两段。
4. 追问里出现了全新的问题时，按 Stage 2 的方式处理。

## Stage 5 - Final Remarks

按模板 9 写 `final-remarks.md`：

1. 输入：每位 reviewer 的压缩上下文（包含追问）、Stage 1 里的初始评分，以及 reviewer 明确表示过变化的最终评分。最终评分向作者确认。
2. 四个部分的顺序不变。每个占位符按模板 9 表格里对应一行的说明来填。
3. 优点：综合所有 reviewer 写 4 到 5 条。问题表格：只写实质性问题（笔误、措辞修改和简单的澄清不写），reviewer ID 要对，每行给一句具体的回复。
4. reviewer 的引文一字不差；分数变化只写明确表示过的。
5. 读者是 Area Chair：这份文字要能独立看懂。
6. 按 Stage 3 的方法统计字符数并报告。向作者确认发给 AC 的这条评论适用哪个长度上限。

## 其他任务

| 请求 | 做法 |
| --- | --- |
| 催促没回复的 reviewer；给 AC 写保密说明 | 填模板 10，并保存到 `messages.md`。只做轻度润色：称呼、落款、段落顺序和占位符不动。某句话和实际情况对不上时（比如讨论期已经结束），改掉它并告诉作者改了什么。 |
| “有 AI 味”、“太生硬” | 只对选中的文字做去 AI 腔处理（`references/quality.md` 第 2 节）。 |
| “太长了” | 压缩（`references/quality.md` 第 3 节）。 |
| 加了一条参考文献 | 引用核实（`references/quality.md` 第 5 节）。 |
| 想手动排版 | 从 `references/templates.md` 里拿出对应的模板。 |

## 常见错误

| 错误 | 正确的形式 |
| --- | --- |
| 自创标签（`W1a`、`\color{orange}{\textbf{...}}`） | `${\color{#f26921}\text{Response W1:}}$`，和模板 2 完全一致 |
| 回复块里没有 reviewer 的原话 | 每个回复块都带引用标签和原文引用 |
| 自己发挥的开头、结尾或分段标题 | 用模板 3 和模板 5 |
| 把作者没说过、只是听起来合理的论证写成定稿 | 留占位，或者写成标注为 unconfirmed 的要点草稿 |
| 看名字猜某个 baseline 或已有方法是做什么的 | 用作者所给文件里的事实，否则留占位 |
| 作者什么都没给，却在每个回复块里留三个占位（结论、证据、修改） | 没有任何输入的问题只留一个占位 |
| 照着 reviewer 的条目编子标签（`W1a`、`W1b`） | 原子问题顺序编号：`Weakness-1`、`Weakness-2` |
| 凭感觉判断长度 | 用工具统计，逐部分报告 |
| 还有占位没填，却说“可以直接粘贴” | 写明“草稿，还有 N 处待填”，并附清单 |
